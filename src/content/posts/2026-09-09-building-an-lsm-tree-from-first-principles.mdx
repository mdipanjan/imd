Most of us use a database long before we think about how it stores anything. We write an `INSERT`, get a success response, and move on. But somebody has to decide where those bytes go, how an update changes them, and what survives when the process stops.

Let’s work through those decisions by building the storage for a small payments service. We’ll start with one account and follow what happens as we add records, change balances, and restart the application.

## Just Put It in Memory

Our first account belongs to Maya Sen. It has an ID of `101` and a balance of ₹5,000. Since requests identify accounts by ID, we can use that ID as the key in a map and keep the name and balance as its value:

```text
accounts = {
    101 → ("Maya Sen", 5000)
}
```

<MemoryAccount />

To read the account, we look up key `101`. A ₹1,000 deposit replaces the balance with `6000`. The map holds the latest value, so we can answer the next request directly from memory.

Then we deploy a new version. The process stops, its memory is released, and the new process starts with an empty map. Account `101` is gone. We may have confirmed a balance update seconds earlier, but we now have no record of it.

A routine deployment is enough to erase every account.

The map is still useful for looking things up, but it cannot hold our only copy of the data. Every change we confirm needs to survive a restart. We’ll start by writing records to a file on disk. When Maya’s balance changes, we’ll also need to decide what happens to the old record.

## Append Every Change

Creating Maya’s account means writing her ID, name, and ₹5,000 balance as a line in `accounts.log`. A ₹1,000 deposit then seems to require a small edit: find that line and replace `5000` with `6000`.

That happens to fit. Both balances occupy four characters in this text format. A later balance of ₹10,000 would need five, and the next record might begin immediately after this one. A fixed-width encoding could avoid that particular problem, but we would still have to locate the old record and handle a write that stops halfway through changing it.

For this version, we can leave the old record alone and append the updated account to the end. Creating an account and changing an existing one now use the same write path:

```text
accounts.log

101, Maya Sen, 5000
205, Priya,    8000
310, Rahul,    2000
101, Maya Sen, 6000
```

<AppendLog />

The file contains two versions of account `101`. We treat the last complete record for an ID as its current value, so Maya’s balance is ₹6,000. The earlier ₹5,000 record still occupies space; it has simply been superseded. This is an **append-only log**, with records arranged in the order we wrote them.

Writing to a file still needs some care. The operating system can buffer writes in memory, so a successful `write()` alone does not mean the data would survive a power failure. Before confirming a durable write, we need the required sync operation, such as [`fsync`](https://man7.org/linux/man-pages/man2/fsync.2.html), to succeed. Recovery also needs a way to detect an incomplete final record. Appending gives us a simpler file layout; crash recovery still has work to do.

After a restart, we could read the log from beginning to end and rebuild our map, replacing each account’s value whenever we encounter a newer version. That restores fast lookups while all the current account data fits in memory.

If we want to retrieve values from the file instead, the duplicate records become a problem for reads. Finding the first `101` gives us an outdated balance. A scan from the beginning has to continue to the end to establish which version is newest, and an account that does not exist makes us scan the whole file anyway. Every deposit adds more data for later reads to examine.

We only wanted Maya’s current balance. If we remembered where her newest record began, we could jump straight to it.

## Remember Where the Record Lives

Every time we append a record, we already know where we wrote it. We can keep that position in a map keyed by account ID and look it up when a read arrives. That map is our **index**.

A **byte offset** counts bytes from the start of a file, beginning at `0`. With UTF-8 encoding and a single newline after each record, the four record lines above occupy 20 bytes each. They start at offsets `0`, `20`, `40`, and `60`. Keeping the latest position for each account gives us:

```text
latest_offset = {
    101 → 60
    205 → 20
    310 → 40
}
```

A request for account `101` now finds offset `60` in the index. We jump to that position in `accounts.log` and read the record through its terminating newline, returning Maya’s ₹6,000 balance. Once the index covers the whole log, a missing ID also gives us an answer immediately: there is no account to retrieve.

Maya then deposits another ₹500. We append her updated account with a balance of ₹6,500 at offset `80`, make the write durable, and change the index entry from `60` to `80` before confirming the update. The next read follows the new position. We never need to search for either of her older records.

<OffsetIndex />

The full account records stay in the file. RAM holds their IDs and offsets, which can save memory when the records are large. The index still needs one entry per account, though, so the number of distinct accounts still matters.

On restart, the index disappears with the rest of the process’s memory. We rebuild it by scanning the log from beginning to end and recording each complete, valid record’s starting offset. Whenever an ID appears again, its newer offset replaces the previous one. For Maya, the entry moves through `0`, `60`, and `80`, finishing at the record with her current balance.

This moves the full scan from every lookup to startup. As the log grows, that startup scan becomes more expensive.

After a thousand more updates to Maya’s balance, the index still has one entry for her. The file has a thousand more records. Reads can skip the old versions now, but they still consume disk space and take time to scan during recovery. We need a way to reclaim that space while the service continues accepting writes.

## Split the Log into Segments

The index tells us which records have been superseded. Removing them is harder. If we rewrite the file the service is still appending to, we have to coordinate incoming writes, records being moved, and reads that already hold offsets into that file.

We can give the cleanup a stable set of files to work on. Put a size limit on the active log, and when it reaches that limit, direct new writes into a fresh file. The old file becomes immutable: we can read it, but we stop adding or changing records inside it. These individual log files are our **segments**.

The index now needs a file name as well as a byte offset. If we rotate after the first four records in our example, Maya’s ₹6,500 update becomes the first record in `segment-02.log`. Her index entry changes to `101 → (segment-02.log, 0)`. A read still goes straight to the latest record; it simply needs to know which file to open.

Once `segment-02.log` has also filled up and closed, writes move to `segment-03.log`. We can now merge the closed files, copying records whose locations still match the index. With Maya’s latest balance at ₹6,500, that keeps her newest record and skips the ₹5,000 and ₹6,000 versions. Combining files is **merging**; removing obsolete versions is **compaction**. Here we do both together.

New deposits continue into the active segment while this runs. Suppose Maya receives another ₹500 during compaction. Her current balance is now ₹7,000, and the index points into the active file. Installing the copied ₹6,500 record must not replace that entry. We relocate an index entry only if it still points to the record we copied, with the check and change performed atomically.

<StorageStory story="segments" />

The replacement is written as a separate file. The inputs remain available until that file is durable, the index entries have been safely relocated, and reads using the old locations have finished. We also need to commit the change in the set of live files atomically and durably before deleting any inputs, so recovery can distinguish a completed replacement from an abandoned partial file. File-set bookkeeping of this kind is the job of the [manifest in LevelDB](https://github.com/google/leveldb/blob/main/doc/impl.md#manifest).

Copying a record must preserve its place in the write history, too. A replacement file created today may contain yesterday’s balances. Its creation time cannot make those balances newer than deposits already written to the active segment.

Compaction reclaims space and reduces the history we scan during recovery, at the cost of reading and rewriting data in the background. It shares disk bandwidth with the application, so it needs enough capacity to keep up with incoming updates. Splitting the log makes that work manageable; rotation alone does not reclaim any space.

This arrangement is already a useful storage design, broadly similar to [Bitcask](https://riak.com/assets/bitcask-intro.pdf). Its hash index works well for looking up individual accounts, but it gives us no ordering between them. A request for accounts `100` through `300` still has us checking keys in the hash table and retrieving records scattered across files. Sorting the records within each completed segment would give us a more useful layout for those reads—and another way to merge files.

## Sort the Records by Key

In a file sorted by account ID, accounts `100` through `300` sit together. Once we find the start of that range, we can read forward and stop when the next ID exceeds `300`. The file’s order now tells us which records we can skip.

We’ll use that layout for completed batches of writes. For the current-balance reads in our example, each batch needs only its last update for an account. We write those records in account-ID order into a new immutable file: a **Sorted String Table**, or **SSTable**. The name comes from treating keys and values as byte strings; our keys still represent account IDs. The [Bigtable paper](https://storage.googleapis.com/gweb-research2023-media/pubtools/4443.pdf) describes this combination of ordered records, individual lookups and range scans.

Sorting a batch does not remove older versions in other files. An earlier batch and a later one might produce these tables:

```text
Earlier writes                  Later writes
101 → Maya Sen, 6500             101 → Maya Sen, 7000
205 → Priya,    8000             150 → Ananya,   4000
310 → Rahul,    2000             205 → Priya,    9000
```

To merge them, we compare the next unread account in each file. Both start with `101`, so we write Maya’s later ₹7,000 record and advance both inputs. We now have `205` on the left and `150` on the right. Copy `150` and advance only the right input. The two `205` records meet next; keep Priya’s ₹9,000 update. Rahul’s `310` is the remaining record.

<StorageStory story="sorted-merge" />

The output is sorted, and every input moves forward. We need buffers for the records being read and written, so the merge can handle files much larger than RAM. The same approach extends to more files by repeatedly choosing the smallest next key.

The labels “earlier” and “later” describe the writes. After compaction, one file may contain records from several batches. We can preserve their ordering by assigning each write an increasing sequence number and carrying it with the record through every rewrite. For matching account IDs, that number tells us which update wins. A file’s creation time cannot do that.

Sorted order also gives us a way to reduce the index. We can divide each table into blocks and record the first key and file position of each block. Suppose one block starts at `101` and the next at `310`. If `205` exists in this table, it must be in the first block. We binary-search the block index, read that block, and search within it. This is a **sparse index**: an entry can guide us to many records. [LevelDB’s table format](https://github.com/google/leveldb/blob/main/doc/table_format.md) likewise has one index entry per data block, using boundary keys to locate the block.

<StorageStory story="sparse-index" />

For completed tables, these smaller indexes can replace the global map of every account’s exact location. The tradeoff is that a lookup may now consult several files containing the same account ID. A range read similarly scans the relevant part of each table and merges the results, resolving duplicate IDs by write order. Recent writes must participate in those reads as well; for now, the active log can keep its own index.

That leaves the write path. Deposits arrive in whatever order customers make them. We could reread and sort each closed log before producing its SSTable, but we already handle every update as it arrives. Keeping a bounded batch ordered in memory would let us write it out sequentially when it fills.

## Sort Live Writes in Memory

An ordered map can hold the current batch of account records and return them in key order whenever we need to write a file. A balanced search tree gives us the operations we need: insert a new account, replace its value, look it up, and walk through the keys in order. This working batch is our **memtable**.

Writes to accounts `310`, `101`, `205` and `150` can arrive in that order; walking the tree still yields `101`, `150`, `205`, `310`. Each entry holds the account record and its write sequence number. We keep the append log alongside it, but recent reads can now get their values from memory.

Suppose Priya’s ₹9,000 balance is in an SSTable. A ₹500 deposit puts `205 → ("Priya", 9500)` into the active memtable. Further changes to her account replace that entry with the latest value and sequence number. For the current-state reads we are building, the batch needs only its latest version of each account.

We give the memtable a memory budget, accounting for both records and the structure that holds them. When it reaches that budget, we freeze it and direct subsequent writes into a new memtable. The frozen one can be walked in key order to produce an SSTable, including its block index. Writing this batch to a new file is called **flushing**. The [RocksDB memtable documentation](https://github.com/facebook/rocksdb/wiki/MemTable) describes the same active-to-immutable handoff.

Priya receives another ₹300 while that flush is running. The update belongs to the new active memtable, so her record can now appear in three places:

```text
Active memtable      205 → Priya, 9800
Frozen memtable      205 → Priya, 9500   (being flushed)
Existing SSTable     205 → Priya, 9000
```

<StorageStory story="memtable" />

A lookup checks the active memtable first, then any frozen batches from most recent to oldest. Here it returns ₹9,800 immediately. If the account is absent from those batches, the lookup continues into the relevant SSTables, using sequence numbers to resolve versions across files. Range reads merge the ordered records from these sources.

The frozen batch remains available to readers until its SSTable is complete and safely installed in the live file set. Reads already using the old batch must also finish before its memory is freed. Completing the flush of Priya’s ₹9,500 record changes where that version lives; it does not replace the ₹9,800 value in the active batch.

If new batches fill faster than storage can flush them, frozen batches accumulate. We need a limit on that backlog and a way to slow or pause incoming writes when it is reached.

Recent reads now use the memtable, and completed batches become sorted files without another pass over the log. The log still has an essential job: protecting the records that have not reached an installed SSTable.

## Protect Recent Writes with a WAL

Priya’s ₹9,800 balance may still be in memory when the machine loses power. The SSTables alone cannot recover it yet. This is why we kept appending updates to the log while changing the structures used for reads. In this role, the append log is a **write-ahead log**, or **WAL**: a recovery record written before the update reaches its final table on disk.

For this version, we apply writes in sequence order. Recording Priya’s update follows this path:

```text
Append (sequence, 205, "Priya", 9800) to the WAL
Sync the WAL successfully
Apply the record to the active memtable
Return success
```

<StorageStory story="wal" />

The sync is part of our durability promise. As we saw earlier, handing bytes to the operating system is insufficient for surviving a machine failure. Creating a new WAL also requires [making its directory entry durable](https://www.man7.org/linux/man-pages/man2/fsync.2.html). Several updates can share a sync, provided each waits for the operation covering its record before being acknowledged. [LevelDB’s synchronous-write documentation](https://github.com/google/leveldb/blob/main/doc/index.md#synchronous-writes) explains this distinction and how batching can spread the sync cost.

After a crash, recovery loads the recorded live SSTable set and replays the WALs still needed for unflushed batches. Their records rebuild the memtable in write order. Replaying Priya’s record installs the stored ₹9,800 balance; it does not run the ₹300 deposit again. We retain the recorded sequence numbers and resume numbering beyond the recovered write history.

The log needs enough structure to distinguish a whole record from a torn write. A stored length helps identify an incomplete record, and a checksum helps detect damage; [LevelDB’s log format](https://github.com/google/leveldb/blob/main/doc/log_format.md) includes both. An incomplete final record left by an interrupted append can be discarded. Damage to earlier history needs to be reported rather than silently treated as an unfinished last write.

A crash after the sync but before the memtable update is recoverable through the same replay. It can also happen before the success response reaches the caller. A missing response therefore leaves the caller uncertain whether its update took effect. Retrying a deposit safely needs an application-level request identity or equivalent deduplication rule; recovering a stored balance alone does not provide that.

We can pair each memtable with its own WAL and rotate them together: freeze batch A and its log, then begin batch B with a new log. A’s log remains available throughout its flush. [RocksDB’s WAL lifecycle](https://github.com/facebook/rocksdb/wiki/Write-Ahead-Log-%28WAL%29) makes the general retention rule explicit: a log stays necessary while it contains updates that still depend on it for recovery.

Writing A’s SSTable is only the first step. We must make the file durable, including the filesystem work needed to preserve its name, then durably record its installation and the fact that A’s WAL is no longer needed. The manifest introduced earlier holds this recovery bookkeeping; [RocksDB’s manifest documentation](https://github.com/facebook/rocksdb/wiki/MANIFEST) describes how it records the live database state. Only after that handoff can we delete the old WAL.

If the machine stops before the handoff is committed, recovery still has A’s log. If it stops afterwards, the recorded file set includes the completed SSTable. An obsolete WAL left behind by a crash can be cleaned up later. The ordering matters because deleting the log first could leave us with neither a usable table nor the records needed to rebuild one.

We now write an update to the log promptly and place it in a sorted file later, together with the rest of its batch. Those writes pay for different things: the first allows a durable acknowledgement; the second gives subsequent reads an ordered layout.

## Putting the Storage Engine Together

Consider one more ₹200 deposit into Priya’s account. Her balance becomes ₹10,000. The engine assigns the update a sequence number, appends the full record to the WAL and syncs it. It then updates the memtable and confirms the write. A read can return the new balance while its eventual SSTable is still some time away.

When the batch fills, it becomes immutable and a fresh batch takes over. Flushing writes the ₹10,000 record in account-ID order alongside the other records in that batch. Once the new table is durable and registered, the batch’s recovery log can be retired. Later compaction merges that table with others and removes superseded versions that the engine no longer needs to retain. The sequence number keeps the deposit’s place in the history even as its file and offset change.

<StorageStory story="lifecycle" />

This is the core of a **Log-Structured Merge-tree**, usually shortened to **LSM-tree**. Updates accumulate in memory, become sorted files in batches, and are consolidated through merging. The WAL makes the time between accepting an update and flushing its batch recoverable.

As the database grows, choosing which files to merge becomes a substantial part of the design. One common approach is **leveled compaction**. Newly flushed tables enter level 0, where their key ranges can overlap. Compaction merges selected files with overlapping ranges in a deeper level. Within each level below level 0, the files cover non-overlapping key ranges, allowing a lookup to narrow its search by range. [RocksDB’s leveled-compaction guide](https://github.com/facebook/rocksdb/wiki/Leveled-Compaction) illustrates this organization.

Those levels group SSTables for searching and compaction. In the layout described here, the memtables live in RAM; the WAL and SSTables at every level live on durable storage.

There is a cost to maintaining this arrangement. An update can be written to the WAL, written again during a flush, and rewritten during several compactions. That extra disk traffic is **write amplification**. Keeping more files around can reduce some immediate merging work, while making reads examine more places and allowing obsolete versions to consume space. The compaction policy decides how to spend that work.

Our example has focused on storing and retrieving current account records. Deletion adds another requirement: a marker must hide older versions until they can be safely removed. Snapshot reads require retaining versions that an older reader can still observe. A complete payments database also needs rules for transactions and concurrent account updates. These build on the storage design we have worked through.

The first version of the service lost an account during a routine restart. In this design, an acknowledged update has a recovery path through the WAL while its batch is in memory, then through a registered SSTable after the flush. We can move and reorganize the record without changing the balance the application sees.
